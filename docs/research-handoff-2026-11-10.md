## 中性名称的真实含义

`unknown_256`、`unknown256`、`GLOBAL_...` 等是归并时新增的占位名，不能直接
作为游戏存在未知行为的证据。初始快照中的 3,789 条占位分布如下，按作品、
命名空间及 opcode／变量 ID 计数；同一项可在两套风格中重复出现。

| 原因 | zero318 风格 | Priw8 风格 |
| --- | ---: | ---: |
| 另一来源已有名称，本风格未建立对应 | 420 | 731 |
| 两家该作 map 均未命名，来自编译器签名表或变量类型声明 | 1,319 | 1,319 |
| 合计 | 1,739 | 2,050 |

第二类包含 thecl 回退到历史版本表而得到的条目。尚未确认这些编号在对应游戏中
实际实现；不能把编译器可查询集合当成原作指令集合，也不能据此计算待逆向规模。

第一类也不都表示用途未知。例如 TH06 opcode 1 在 zero318 中为 `enemy_delete`，
Priw8 风格仍生成 `unknown1`；TH11 opcode 89 在 Priw8 中为 `linearFunc`，
zero318 风格生成 `unknown_89`。

## 签名与类型分歧

【证据支持：源码和 map 文本比较】记录了 228 条 zero318 `_thtk` 签名与
thecl 内置表的差异。Priw8 的这些文件通常不含签名，因此这个数不表示
228 条 Priw8／zero318 签名冲突。同一差异在多个作品出现时重复计数。

| 差异形状 | 条数 |
| --- | ---: |
| 同宽整数的符号性、时间等标注不同，仍可能影响解析或源码表示 | 100 |
| 字段数量或布局不同 | 88 |
| 参数类型不同 | 38 |
| 变长参数定义不同 | 2 |

分作品为 TH08 51、09 48、10 14、11 19、12 11、15 7、18 7、185 8、19 37、20 26。
这个比较不包含仅有 truth 格式的文件，也不包含 zero318 缺作；未列出不表示无分歧。

后续可用以下具体条目作为切入点；当前没有裁定哪边正确：

| 作品／opcode | zero318 名称 | zero318 签名 | thecl 内置签名 |
| --- | --- | --- | --- |
| TH08 timeline 8 | `boss_interrupt` | `SS` | `Sss` |
| TH10、11／87 | `math_line_angle` | `ffff` | `fffff` |
| TH12／527 | `std_interrupt` | `S` | 空 |
| TH15、18、185、19、20／92 | `math_float_interp_bezier` | `SfSSffff` | `SfSSff` |
| 同上／324 | `enemy_id_get_position` | `ffS` | `S` |
| TH185、19／1014 | `__write_float_array` | `Sffffffff` | `S` |
| TH19／535 | `enemy_no_collision_timer` | `S` | `SSSSSSSSS` |
| TH19、20／550 | 见原始 map | `m` | `m*D` |

另有 6 条全局类型分歧，都指向 ID `-9961`：TH10、11、12、15、18、185 中

或 `ANM_SLOT0_ID`；Priw8 名称为 `UNKNOWN61` 或 `ANM_ID`。
这是同一编号在六作的记录，不应直接称作六种独立机制错误。

## 名称层面的比较结果

在共同有 map 的 TH08、10、11、12、15、18、185 中，定向检查暂未找到
“zero318 明确使用 unknown 类名称，而 Priw8 已给出明确语义名称”的例子。
TH10 按 Priw8 的声明复用 TH11 文件。这是已检查范围内的未发现，不能推广到
其他作品、其他版本提交或全部社区资料。

已找到的互补情况包括：

## 已纠正的取舍与现阶段边界

1. 初始导入直接以 thecl 内置签名为共用层基线。这个规则只复现编译器默认查表，
   对有参数数量和布局争议的条目，不能作为语义裁决。该选择保留在快照中供复核，
   不再作为接入 Studio 的理由。
2. 初始对应规则把所有 `__...` 都排除，并要求跨作名称及签名对应唯一。
   这是导入时的保守筛选，会制造风格缺名；不能把筛选结果说成上游研究空白。
3. 初始导入给所有编译器继承条目补名，扩大了表面上的未知集合。
   后续先确认本作实际分派和有效 opcode，再决定是否保留这些条目。
4. 相同名字、相同参数签名和相同 opcode 位置都不足以单独证明跨作行为相同。
   fork 自动推导的名称保持候选状态；类型来源优先级也不是逆向结论。

用户已决定把这些问题留待后续逆向。当前不继续扩大名称自动归并，不批量改写已有
ECL 源码，不把该草稿替换为 Studio 默认 map，不修改编译器或扩展研究平台。
后续以目标游戏中的读参、字段转换、状态消费者和可观察结果决定真实语义；
两套名称作为同一已确认语义的别名维护，不需要先选定哪位作者处处正确。

## 后续研究的最小入口

以下是恢复入口，不是本轮已启动的研究计划：

- 先选一个具体游戏版本和少量有判别力的条目，例如 TH18／92、324，或 TH12／527。
- 登记游戏版本与补丁、可执行文件 hash、ECL 样本来源及对应的持久 Ghidra 工程。
  本轮没有登记目标游戏样本，也没有新建、打开或修改游戏的 Ghidra 工程。
- 找到该游戏的 ECL 分派及参数读取路径，确认编号是否存在、读参类型、数量、顺序，
  再跟随结果的写入者与消费者确定用途。若涉及差异版本，分别保留证据。
- 能取得真实 ECL 数据或运行表现时交叉核对；只做静态分析时，结论注明覆盖范围。
- 研究结果落到对应游戏／命名空间／编号，再修正共用签名、两套名称和证据记录。
  Studio 的默认 map 与按版本、风格选择等接入工作后续单独恢复。

当前证据类型只有外部源码、社区 map 和加载器观察；没有游戏内语义闭环。
原有项目可能另有研究工程，恢复时先读项目约定和已有记录，不把本次未使用
Ghidra 理解为没有可复用工程。
